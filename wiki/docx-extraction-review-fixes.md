# ТЗ: исправления DOCX extraction в PR #10

**Контекст:** PR [#10 — DOCX extraction and structured chunk metadata](https://github.com/gregkorneev-BMSTU/study-agent/pull/10), ревизия `40e37db`. Документ превращает замечания ревью в проверяемый план реализации. Это ТЗ, не описание уже существующего поведения.

## 1. Цель

Исправить три проблемы до включения PR #10 в `main`:

1. Сохранять исходный порядок абзацев и таблиц DOCX и правильный контекст заголовков.
2. Не терять предупреждения об ошибках извлечения: пользователь должен видеть, какие документы не удалось обработать, при этом остальные результаты поиска остаются доступны.
3. Не создавать постоянные копии `.txt` и `.md` в OCR-кэше и не добавлять им лишнее чтение/хеширование.

Сохранить локальную обработку, текущий bridge и существующий UX поиска. Не менять Python backend, формат JSON Lines транспорта, индексирование или архитектуру приложения за пределами необходимого для этих исправлений.

## 2. Порядок и контекст содержимого DOCX

### Требования

- Обходить верхнеуровневые абзацы и таблицы в том порядке, в котором они расположены в документе.
- Сохранять существующее представление таблицы строками с разделителем ячеек, если это не приводит к потере текста.
- Привязывать абзац и таблицу к действующему пути заголовков на момент их появления в документе. Не назначать всем таблицам заголовок последнего раздела.
- Учитывать уровни стилей Word `Heading 1`, `Heading 2` и далее: при переходе к заголовку уровня N удалить из контекста заголовки уровня N и глубже, затем добавить новый заголовок. Например, блоки под `Heading 2` должны сохранять контекст родительского `Heading 1`.
- Текущий DTO содержит `heading: str | None`. Не менять его тип только ради этой задачи: передавать полный breadcrumb в детерминированном человекочитаемом виде либо предложить отдельное изменение контракта и явно согласовать его с потребителями до реализации.
- Маркеры абзацев, заголовков и таблиц должны оставаться детерминированными внутри одного документа и не конфликтовать между типами блоков.
- Обрабатывать пустые абзацы/строки таблиц без создания пустых блоков. Не изменять исходный DOCX.

### Критерии приёмки

Для синтетического документа `Heading 1 → paragraph A → table A → Heading 2 → paragraph B → table B → Heading 1 → paragraph C` извлечённые блоки:

- идут точно в указанном порядке;
- сохраняют все непустые тексты абзацев и таблиц;
- для `paragraph A` и `table A` содержат контекст первого `Heading 1`;
- для `paragraph B` и `table B` содержат контекст первого `Heading 1` и вложенного `Heading 2`;
- для `paragraph C` содержат только второй `Heading 1`.

### Проверки

- Добавить тест на порядок «абзац — таблица — абзац» с настоящим синтетическим DOCX через `python-docx`, чтобы фикстура проверяла реальные XML-отношения, а не только отдельно подготовленные списки `paragraphs` и `tables`.
- Добавить тест на переходы между уровнями заголовков и контекст таблицы внутри раздела.
- Убедиться, что текст после извлечения остаётся доступным поиску.

Поддержка вложенных таблиц, колонтитулов, сносок, текстовых полей и расположения элементов Word на страницах не входит в это ТЗ. Если они не обрабатываются, это должно оставаться явно описанным ограничением, а не создавать ложное обещание о полном извлечении DOCX.

## 3. Видимые предупреждения извлечения

### Требования

- Сохранить изоляцию ошибок: сбой OCR одной страницы или ошибка разбора одного DOCX не должны останавливать поиск по остальным документам.
- Передать предупреждения из `ExtractedBlock.warnings` до результата команды `search`. Одного хранения предупреждения в DTO недостаточно, если слой поиска его выбрасывает.
- Ответ `search` должен сообщать одновременно найденные совпадения и документы/страницы, которые не удалось извлечь. Отсутствие совпадений не должно скрывать ошибку обработки.
- Предупреждение должно позволять определить документ по относительному `document_id` и отображаемому имени. Не включать абсолютные локальные пути, содержимое документа, текст OCR-контекста или traceback в пользовательский ответ.
- Передавать стабильный машинный код предупреждения, если его можно показать на русском и английском через локализацию UI. Не показывать необработанный текст исключения из сторонней библиотеки пользователю.
- Не менять формат успешных `hits` без необходимости. Дополнительное поле предупреждений должно быть обратно совместимым для клиентов, которые его не читают.
- Если обновляется macOS UI, показывать локализованное доступное предупреждение рядом с результатами поиска: например, «Не удалось прочитать 1 документ» со списком затронутых документов. Пустое состояние поиска должно отличаться от ошибки извлечения. VoiceOver должен объявлять предупреждение.
- Сохранять показ успешных результатов рядом с предупреждениями. Не заменять частичный результат общим ошибочным экраном.

### Проверки

- Повреждённый DOCX возвращает диагностируемое предупреждение и не создаёт ложный текстовый hit.
- Ошибка OCR отдельной PDF-страницы возвращает предупреждение с относительным ID документа и номером страницы, если он известен; последующие страницы и другие документы продолжают обрабатываться.
- При поиске, который одновременно нашёл один документ и не смог извлечь другой, результат содержит hit и warning.
- При отсутствии hits предупреждение всё равно возвращается и UI отображает его.
- Пройти отображение сообщения в русском и английском языках; проверить длинное имя файла и клавиатурную/VoiceOver доступность, если изменяется SwiftUI UI.

## 4. Границы кэширования

### Требования

- `.txt` и `.md` читать напрямую и превращать в один `ExtractedBlock`; не вычислять для них SHA-256 только ради кэша, не писать их содержимое в `Application Support/Study Agent/OCR`.
- Сохранить кэш для дорогих PDF/image extraction и OCR. В рамках этого PR DOCX не кэшировать, если отдельное измерение не показывает, что повторный разбор заметно ухудшает поиск.
- Ключ кэша продолжает учитывать содержимое исходного файла, чтобы изменение файла не возвращало устаревший текст.
- Кэш и временные файлы остаются вне исходных пользовательских каталогов и Git checkout. Не удалять старые пользовательские кэш-файлы автоматически в ходе миграции.
- Ошибка записи необязательного кэша не должна портить исходный документ или терять уже извлечённый результат. Временный файл следует убирать при неудачной записи/замене; ошибку кэша нельзя путать с ошибкой извлечения.

### Проверки

- Подменить `_cache_path` шпионом и подтвердить, что чтение `.txt`/`.md` не вызывает его и не создаёт кэш.
- Дважды прочитать текстовый файл и получить одинаковый блок, не создавая вторую копию содержимого.
- Для PDF/изображения подтвердить повторное использование OCR-кэша и повторное извлечение после изменения исходного содержимого.
- Проверить, что неудачная запись кэша не меняет успешный результат извлечения и не оставляет временные файлы.
